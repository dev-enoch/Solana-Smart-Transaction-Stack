1. Executive Summary
Modern Solana applications require far more than simply submitting transactions through an RPC endpoint. Between transaction creation and finalization, transactions pass through multiple stages of the Solana network including leader scheduling, TPU ingestion, block production, shred propagation, and commitment confirmation. Production-grade infrastructure must understand these stages, react intelligently to failures, and adapt dynamically to changing network conditions.

This project implements a complete smart transaction infrastructure stack that combines Yellowstone gRPC streaming, Jito bundle submission, lifecycle observability, and AI-powered operational decision making.

The system continuously observes live network conditions using Yellowstone (Geyser) streams, identifies optimal leader windows for submission, dynamically calculates Jito tips based on real network fee data, submits transaction bundles through the Jito Block Engine, and tracks every transaction throughout its lifecycle from submission to finalization.

In addition to monitoring and execution, the stack introduces an AI-powered operational layer capable of diagnosing transaction failures and making autonomous retry decisions. Rather than relying on hardcoded retry logic, the AI agent evaluates failure context, determines root causes, recommends corrective actions, and initiates recovery workflows when appropriate.

The result is a transaction infrastructure platform that demonstrates how Solana transactions move through the network while satisfying all requirements of the Smart Transaction Infrastructure bounty.

3. System Architecture Overview
The transaction stack is organized into five primary layers:
- Ingestion Layer
- Core Transaction Engine
- Decision Layer
- Tracking and Observability Layer
- Submission Layer

Each layer is responsible for a specific operational concern and communicates through asynchronous message passing using Tokio channels and shared state primitives.

Architectural Layers

Ingestion Layer
Responsible for collecting real-time Solana network data through Yellowstone gRPC subscriptions.
Primary responsibilities include:
- Slot streaming
- Transaction streaming
- Leader schedule tracking
- Reconnection management
- Backpressure handling

Core Transaction Engine
Responsible for transaction creation and bundle preparation.
Primary responsibilities include:
- Memo transaction construction
- Dynamic tip calculation
- Blockhash management
- Bundle assembly
- Jito payload generation

Decision Layer
Responsible for intelligent operational decisions.
Primary responsibilities include:
- Failure reasoning
- Retry strategy generation
- Tip adjustment recommendations
- Submission timing recommendations

Tracking and Observability Layer
Responsible for transaction lifecycle monitoring.
Primary responsibilities include:
- Commitment tracking
- Latency measurement
- Failure classification
- Lifecycle persistence
- Operational telemetry

Submission Layer
Responsible for communication with the Jito Block Engine.
Primary responsibilities include:
- Bundle serialization
- Bundle submission
- Bundle response handling
- Error propagation

The following workflow describes the interaction between all major components.
1. Yellowstone continuously streams slot and transaction updates.
2. The orchestrator processes stream events.
3. The leader schedule cache determines whether a favorable Jito leader window is approaching. If a target slot is requested or a window isn't found within a fallback threshold, it submits anyway.
4. The Tip Manager calculates an optimal tip using live prioritization fee data.
5. The Bundle Builder constructs a transaction bundle.
6. The bundle is submitted to the Jito Block Engine, adhering to a 1 request/sec rate limit.
7. The Lifecycle Tracker monitors commitment progression via Yellowstone stream and a secondary RPC polling fallback.
8. Failures are analyzed by the AI Agent.
9. The AI Agent determines whether to retry, increase tips, refresh blockhashes, delay submission, or abort.
10. If the AI is unavailable or the retry limit is exceeded, deterministic fallback logic triggers.

5. Core Components

5.1 Yellowstone Streamer
Purpose
The Yellowstone Streamer serves as the real-time ingestion layer of the system.
It maintains a persistent gRPC connection to a Yellowstone (Geyser) endpoint and streams live Solana network events.

Responsibilities
- Subscribe to slot updates
- Subscribe to transaction updates
- Maintain leader schedule cache
- Detect upcoming Jito leaders (look-ahead 4 slots)
- Handle automatic reconnection with exponential backoff

5.2 Tip Manager
Purpose
The Tip Manager dynamically determines the optimal bundle tip required for successful transaction inclusion.
Rather than relying on hardcoded tip values, the system continuously analyzes recent prioritization fee activity and adjusts bundle tips according to current network conditions.

Responsibilities
- Fetch prioritization fee data
- Maintain recent fee history
- Calculate congestion-adjusted tips
- Prevent underbidding during congestion
- Prevent excessive overpayment during low traffic periods

5.3 Bundle Builder
Purpose
The Bundle Builder constructs transaction bundles and submits them to the Jito Block Engine.

Responsibilities
- Create bundle payloads
- Append tip transactions
- Sign transactions
- Serialize transactions
- Submit bundles through JSON-RPC

Submission Workflow
1. Obtain a fresh blockhash via RPC.
2. Calculate the dynamic tip.
3. Build memo transaction.
4. Build tip transaction.
5. Assemble bundle.
6. Serialize transactions.
7. Submit bundle to Jito Block Engine.
8. Dual-submit the underlying transaction via standard RPC with `skip_preflight: true` as a robust fallback.
9. Record lifecycle metadata.

5.4 Lifecycle Tracker
Purpose
The Lifecycle Tracker provides end-to-end observability for every submitted bundle.
Every transaction progresses through multiple commitment levels: Submitted -> Processed -> Confirmed -> Finalized

Recorded Metrics
For every bundle the tracker stores:
- Bundle ID
- Submission slot
- Processed slot
- Confirmed slot
- Finalized slot
- Tip amount
- Failure classification
- Processing latency
- Confirmation latency

5.5 AI Agent
Purpose
The AI Agent owns operational decision making inside the transaction stack.
Unlike purely deterministic retry systems, the agent evaluates transaction failures and determines how the system should respond by calling an LLM (Gemini, Grok, OpenAI, or Ollama).

Inputs
The AI agent receives a Failure Context containing:
- Bundle ID
- Failure type
- Current slot
- Tip amount
- Transaction latency
- Extra contextual details
- Detailed retry history for the bundle chain
- Network snapshot (recent priority fees, tip accounts, Jito leader distance, landing rates)

Outputs
The agent outputs structured JSON with its reasoning, root cause, and the next best action:
- `refresh_blockhash`: Refresh the blockhash and resubmit.
- `retry_higher_tip`: Increase tip and resubmit.
- `wait`: Wait a specified number of slots before retrying.
- `abort`: Stop retrying.

This satisfies the bounty requirement that retry decisions originate from the agent itself rather than hardcoded procedural logic, while maintaining strict fallback safety nets.

6. Failure Recovery Pipeline
The failure recovery loop implements an exact sequence of steps to handle unconfirmed or expired bundles:

1. **Failure Detection:** The Lifecycle Tracker detects an expired blockhash or a failed transaction signature from the Yellowstone stream.
2. **Retry Cap Check:** The system checks if the intent has exceeded the strict cap of 8 retries (MAX_RETRIES). If so, it abandons the bundle.
3. **AI Decision:** An asynchronous task calls the AI Agent with the failure context and the summary of past retry attempts.
4. **Action Execution:** 
   - If the AI returns `refresh_blockhash`, a new intent is queued to fetch a new blockhash.
   - If the AI returns `retry_higher_tip`, a new intent is queued with the suggested higher tip.
   - If the AI returns `wait`, the system queues an intent with a target slot (current slot + wait_slots).
   - If the AI returns `abort`, the intent is dropped.
5. **Deterministic Fallback:** If the AI API request fails, times out, or returns invalid JSON, the system falls back to a deterministic routine: it queues a retry with a refreshed blockhash and a 1.5x tip multiplier.
6. **Re-Submission:** The Orchestrator pops the new intent and waits until the target slot is reached and a Jito leader is active in the upcoming 4 slots. If a Jito window is not found within 5 slots of the target, the bundle is submitted anyway as a fallback.

7. Infrastructure Design Decisions

Why Yellowstone gRPC is used
Yellowstone Geyser gRPC streaming is used instead of standard RPC polling because it provides push-based, sub-second updates for slots and transactions directly from the validator. This significantly lowers latency and reduces network overhead, which is critical for timing-sensitive transaction observability and leader window tracking.

Why Jito Block Engine is used
The Jito Block Engine allows the system to bypass the public mempool by submitting transactions as bundles with direct tips to Jito validators. This guarantees atomicity, reduces the likelihood of MEV frontrunning, and provides higher inclusion guarantees during periods of network congestion.

Tradeoffs between Yellowstone and RPC polling
- **Yellowstone:** Provides near-instant updates and accurate slot progression, but requires maintaining a persistent gRPC connection, handling disconnects, and writing exponential backoff logic.
- **RPC Polling:** Simpler to implement via HTTP requests, but introduces high latency, misses intermediate commitment states, and can quickly hit rate limits.

RPC Fallback Strategy & Preflight Bypassing
While the primary ingestion relies on Yellowstone, the system runs parallel standard RPC fallback mechanisms for both monitoring and submission:
1. **Submission Fallback (Dual-Submission):** The Bundle Builder simultaneously submits the transaction to the standard RPC endpoint alongside the Jito Block Engine. This guarantees inclusion on networks (like Devnet) where Jito bundles are frequently dropped or validators are scarce. Crucially, the standard RPC fallback uses `skip_preflight: true`. This circumvents false `Blockhash not found` simulation errors caused by public load-balancers routing preflight checks to nodes with lagging block heights.
2. **Monitoring Fallback:** An asynchronous task polls standard RPC signature statuses every 8 seconds. If Yellowstone drops a message or disconnects, the RPC polling ensures that transaction confirmations are still reliably tracked.

Regional Latency Considerations for Block Engine
The Jito Block Engine operates multiple regional endpoints. The system connects to the Amsterdam endpoint (`amsterdam.mainnet.block-engine.jito.wtf`) by default, but this can be overridden via environment variables. Choosing the endpoint closest to the host infrastructure minimizes bundle submission latency, increasing the chance of landing in the narrow Jito leader window.

Why Tokio Channels were selected
Tokio's Multi-Producer Single-Consumer (mpsc) channels (`mpsc::channel::<StreamEvent>`) were selected to decouple the synchronous ingestion of gRPC streams from the potentially blocking logic of transaction orchestrating and tracking. This ensures the Yellowstone stream is never bottlenecked by transaction generation or AI API latency, maintaining optimal real-time performance.

8. Operational Assumptions and Limitations

Current AI Limitations
- The system relies on an external LLM (Gemini 2.5 Flash via REST API). Network latency to the API can delay retry decisions.
- LLMs can occasionally return poorly formatted JSON or hallucinate actions, requiring strict parsing and the deterministic fallback.
- Context windows are limited, so retry history must be summarized rather than providing full transaction logs.

Current Retry Behavior
- Retry loops are strictly capped at 8 retries (MAX_RETRIES).
- Rate limits enforce a maximum of 1 submission per second to Jito.
- The system will wait for an upcoming Jito validator up to 5 slots. If 5 slots pass without a Jito leader, it submits the bundle anyway, assuming it will eventually land or expire.

Known Limitations
- The system currently only generates basic Memo transactions; it does not yet handle complex DeFi swaps where slippage calculations might be affected by retry delays.
- A single RPC node is used for initial blockhash fetching; if this RPC node goes down, bundle building halts regardless of Yellowstone's status.
- The Jito rate limit is hardcoded to 1 req/sec.

Future Improvements
- Implement a smaller, local LLM running directly within the cluster to eliminate API latency and external dependency.
- Expand transaction support to dynamically adjust slippage parameters for DEX swaps during retry loops.
- Implement RPC endpoint failover for blockhash fetching.

9. Benchmark Methodology & Active Telemetry
The stack natively implements real-time performance benchmarking through the Tracking and Observability Layer. 

For every transaction bundle, the system actively records the exact Unix timestamp at each of these stages and persists them to `lifecycle_logs.json`:
1. **Creation Time:** (`submitted_at`) When the intent is generated and submitted.
2. **Processed Time:** (`processed_at`) When the Yellowstone stream emits a `processed` event.
3. **Confirmed Time:** (`confirmed_at`) When the secondary RPC or stream emits a `confirmed` status.
4. **Finalized Time:** (`finalized_at`) When the transaction is `finalized`.

The system automatically calculates and exports the following metrics:
- **Time to Inclusion:** (`latency_processed_ms`) Measures network propagation and Jito Block Engine effectiveness.
- **Time to Confirmation:** (`latency_confirmed_ms`) Measures the cluster voting latency.
- **Cost Efficiency (Tip ROI):** By co-locating the `tip_lamports` with the latency metrics in the logs, developers can effortlessly correlate dynamic tip algorithms against actual inclusion times to ensure the system is not overpaying.
- **AI Decision Latency:** Operational events track the exact time an AI strategy is produced and executed following a failure.
